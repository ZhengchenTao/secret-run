# Incident checklist

> Generated by `secret inventory` from `catalog.toml`. **Nothing is decrypted and no value appears here.** To change the content, change the catalog (`secret add --rotate/--reader`); do not edit this file by hand.

When you suspect a device, a server-side reader (such as the web UI) or a single credential has leaked, **work through these steps in order** (one device identity decrypts every entry encrypted to it, so a lost device means evaluating every entry):

0. **A device or server is lost / compromised**: `secret recipients remove <name>`, then `secret rekey`, then rotate values one by one as below. **`rekey` only stops *new* ciphertext from being encrypted to that key; it cannot revoke values that already leaked** -- the old ciphertext in git history still opens with the old key.
1. **Rotate the value and revoke the old one**: generate a new value where the "Rotate where" column says. **Generating a new value does not invalidate the old one** -- revoke it explicitly: remove the old public key from `authorized_keys`, revoke the old token / OAuth grant / app secret in its console, change the database password and confirm the old one no longer logs in.
2. **Write it back**: `secret edit <entry path>` (or `secret add <entry path> --replace --from-file <file>`), then commit + push. Entries in the "Linked entries" column must be rotated together.
3. **Restart the readers**: per the "Read by" column, restart services and re-run scripts; overwrite materialized files with `secret materialize --force`.
4. **Verify**: `secret check` is all green, and every feature that uses the credential actually works.

Go top to bottom by the "Priority" column: `high` first, `low` last.

Note: `rekey` only changes who new ciphertext is encrypted to. It **does not revoke leaked values**; old ciphertext in git history still opens with the old key. The only real remedy is rotating the value.
