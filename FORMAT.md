# FORMAT — secret-run data repo contract (v1)

> The **single contract** shared by the `secret` CLI (`cli/`, PowerShell) and the web UI (`web/`, .NET). Anyone who wants to change the format changes this document first, bumps `format` in the `[[meta]]` block of `catalog.toml`, then changes the implementations.
> One line: **plain age files + a restricted TOML subset**. Neither side adds custom crypto or wrapping.
> 中文版：[FORMAT.zh-CN.md](FORMAT.zh-CN.md)

## 1. Repository layout

```
FORMAT.md                optional copy of this document
README.md                human entry point
INCIDENT.md              incident checklist generated by `secret inventory` from the catalog (names / where to rotate / who reads it — never values; do not edit by hand)
recipients.toml          recipients (public keys, not secret)
policy.toml              path rules -> recipients
catalog.toml             entry metadata (plaintext, no values)
store/
  .recipients.lock       per ciphertext: hash of the recipient set it was last encrypted to + ciphertext hash (written by the CLI)
  <domain>/<group>/<name>.<type>.age
recovery/
  recovery-identity.age  optional: the recovery identity encrypted with a passphrase (scrypt), created by `secret recovery seal`
.gitattributes           *.age binary
.gitignore               explicit whitelist that keeps any plaintext out of the work tree
```

- Keep the repo **private**. Do not feed it to search indexes or AI knowledge bases.
- Apart from `store/**/*.age` and `recovery/*.age`, **every file in the repo is plaintext**: anyone who can read the repo reads them. So they must contain **no values and nothing a value can be inferred from** (token prefixes, password length, "same password as account X", where the recovery key is kept).

## 2. Encoding and general conventions

| Item | Convention |
|---|---|
| Text encoding | UTF-8, **no BOM**, LF line endings (writers must guarantee this; readers tolerate CRLF and a leading BOM) |
| Unicode | All plaintext metadata (TOML strings, aliases) is normalized to **NFC** before writing; both sides normalize to NFC before comparing |
| Paths in the repo | Forward slashes, relative to the repo root, case-sensitive |
| Hash | SHA-256, lowercase hex |
| Date | `YYYY-MM-DD` |
| Sorting / dedup | Always **ordinal**: byte-wise over the UTF-8 string, case-sensitive. PowerShell must use `[StringComparer]::Ordinal` explicitly (`Sort-Object` / `-Unique` default to culture-aware, case-insensitive — not allowed); .NET uses `StringComparer.Ordinal`. Everything sorted here (`age1…` keys, `store/…` paths) is ASCII, so UTF-16 ordinal equals UTF-8 byte order |
| age | Binary format (no `-a` armor); X25519 recipients only; the recovery copy is the one exception (scrypt passphrase) |

## 3. Restricted TOML

All four TOML files use a subset of TOML 1.0. **Writers may only produce this subset; readers must reject anything outside it rather than guess.** The PowerShell side has a hand-written parser; the .NET side may use a standard TOML library but **must validate the result again**: top level only arrays of tables, values only strings / string arrays / booleans (standard libraries accept integers, inline tables, dotted keys and more).

- The top level contains **only arrays of tables** `[[name]]` (no `[table]`, no dotted keys, no inline tables `{}`). Comment and blank lines may precede them.
- Key/value pairs: `key = value`, any number of spaces or tabs around `=`. Keys are bare keys `^[A-Za-z0-9_-]+$`; no duplicate key within a block.
- Only four kinds of values:
  - basic strings `"…"`: escapes limited to `\"` `\\` `\n` `\t` `\r` `\uXXXX` (`XXXX` must not be in the surrogate range `D800–DFFF`); any other backslash sequence is an error
  - literal strings `'…'` (no escapes, cannot contain `'`)
  - string arrays `["a", "b"]`, may span lines, trailing comma allowed, `[]` allowed, elements only the two string kinds above
  - booleans `true` / `false`
- **No control characters** in either string kind (U+0000–U+001F, U+007F; not even tab — use `\t`). Control characters produced by escapes (`\u0000`–`\u001F`, `\u007F`) are also illegal, except the three escapes `\t` `\n` `\r`.
- Comments: `#` to end of line (a `#` inside a string is not a comment).
- No integers, floats or date types (dates are strings).
- Unknown keys: readers **ignore** them (forward compatibility); unknown table-array names: ignored.

When the CLI rewrites a TOML file it emits the canonical form: one blank line between blocks, keys in the order listed in this document, always basic strings with only the necessary escapes; leading comment lines at the top of the file are kept, comments inside blocks are not guaranteed to survive.

## 4. `recipients.toml`

```toml
# Recipients: public keys are public information. Where private keys live: see §9.
[[recipient]]
name = "laptop"
type = "device"
key = "age1…"
status = "active"
added = "2026-01-01"

[[recipient]]
name = "recovery"
type = "recovery"
key = "age1…"
status = "active"
added = "2026-01-01"
backup = ""
```

| Key | Required | Meaning |
|---|---|---|
| `name` | yes | Matches the path-segment regex of §6, globally unique. Devices default to the lowercased computer name (`secret init` picks it; `--name` overrides). A web UI / other service uses its own name (e.g. `web`); the recovery key is always `recovery` |
| `type` | yes | `device` / `service` / `recovery` |
| `key` | yes | X25519 public key, **must match `^age1[02-9ac-hj-np-z]{58}$`** (lowercase bech32; upper or mixed case is rejected, otherwise one key could hash two ways) |
| `status` | yes | `active` (encrypted to) / `pending` (registered, waiting for approval, **not encrypted to**) / `revoked` (kept for the record, not encrypted to) |
| `added` | yes | Registration date |
| `backup` | recovery only | Set to `"offline <date>"` once the owner confirms the recovery key is stored offline (**never where**); empty or missing makes `secret check` WARN |
| `note` | no | Free-text note (plaintext, nothing sensitive) |

- The same `key` must not appear in two records (ERROR).
- **Recipient groups** are implicit: `@all` = every `active` recipient; `@device` / `@service` / `@recovery` = every `active` recipient of that type.

## 5. `policy.toml`

```toml
[[rule]]
path = "store/**"
recipients = ["@all"]
```

- `recipients`: array of recipient names or groups (`@…`), expanded to a de-duplicated set of public keys. A name that does not exist or is not `active` is ignored and `check` WARNs.
- **The last matching rule wins** (rules are not merged). A ciphertext matched by no rule = ERROR.
- An **empty** expansion = ERROR (the file cannot be encrypted, so writing it is refused); an expansion **without any `recovery` recipient** = WARN.
- Use more rules to narrow who can read what — for example give a web UI (`type = "service"`) only the entries it needs to show, so a compromised web host does not expose everything.

**Glob semantics** (not gitignore-style): `path` is matched **fully anchored** against the repo path of the ciphertext (e.g. `store/personal/ssh/deploy-key.file.age`). As a regex: `**` → `.*`, `*` → `[^/]*`, `?` → `[^/]`, every other character literal; `^` … `$` around it. No character classes; `**/` does **not** match zero segments.

| pattern | path | result |
|---|---|---|
| `store/**` | `store/personal/ssh/a.file.age` | match |
| `store/personal/*` | `store/personal/ssh/a.file.age` | no match (`*` does not cross `/`) |
| `store/**/a.file.age` | `store/personal/ssh/a.file.age` | match |
| `store/**/x.kv.age` | `store/x.kv.age` | no match (`**/` does not match zero segments) |

**Recipient-set hash** (shared by the lock and `check`): take the public-key strings of the expanded rule, de-duplicate, sort ordinally ascending, join with `\n` (no trailing newline), SHA-256 of the UTF-8 bytes.

## 6. `catalog.toml`

```toml
[[meta]]
format = "1"

[[entry]]
path = "work/chat/bot-app"
type = "kv"
title = "Chat bot app credentials"
description = "App ID / App Secret used by the notifier and the chat MCP server"
fields = ["APP_ID", "APP_SECRET"]
tags = ["chat"]
rotate = "Developer console -> App -> Credentials -> Reset secret"
readers = ["tools/notify.ps1", "chat MCP service"]
aliases = ["notes:ops/chat-bot.md#Credentials"]
updated = "2026-01-01"

[[entry]]
path = "personal/ssh/prod-server-pem"
type = "file"
title = "prod server private key"
description = "…"
target = "~/.ssh/prod_server.pem"
acl = "private"
updated = "2026-01-01"
```

- **Value constraints (CLI and web must judge identically)**: `path`, `type`, `title`, `updated` are non-empty strings; `updated` / `added` must be real calendar dates (ASCII digits `YYYY-MM-DD`; `2026-02-30` is illegal); kv `fields` is non-empty; `tags` elements are non-empty; an alias's path part is non-empty after normalization; `target` syntax checks (prefix, segment rules, reserved names) are identical on both sides — the web never materializes but validates the same way. Violating any of them = that entry is ERROR: the CLI `check` reports ERROR, the web marks that entry unusable and **keeps the rest of the site working** (the whole site is unusable only on a TOML parse error, a missing `[[meta]]`, or an unknown `format`).
- The first block of `catalog.toml` is always `[[meta]]` with exactly one key `format = "1"` (a string). Readers must refuse to work on a missing or unknown `format`.

| Key | Required | Meaning |
|---|---|---|
| `path` | yes | Logical path `<domain>/<group>/<name>`, **exactly three segments**. Every segment (the domain included — pick any, e.g. `personal`, `work`, `client-a`) matches `^[a-z0-9][a-z0-9-]*$` and is **not** a Windows reserved name (`con` `prn` `aux` `nul` `com1`–`com9` `lpt1`–`lpt9`). Globally unique |
| `type` | yes | `kv` / `file` / `doc`, see §7 |
| `title` | yes | Human title (any language) |
| `description` | no | Purpose, who reads it; **no values** |
| `fields` | kv only, required | Array of field names (each matches the key regex of §7, no duplicates), in display order; must equal the key set inside the ciphertext (`check` verifies names on its decryption sample) |
| `target` | no (file only) | Where `materialize` writes it, see "Materialize targets" |
| `acl` | no (file only) | `private` (default: Windows breaks inheritance and grants only the current user full control; POSIX `0600`) / `inherit` (follow the directory, e.g. `.pub`) |
| `machines` | no (file only) | Only materialize on these devices; elements must be `device` recipient names; default = every device that can decrypt it |
| `tags` | no | Search tags |
| `rotate` | no | **For the incident checklist**: where to rotate this value (console / system name), e.g. `"Developer console -> Bot -> Reset Token"`, `"regenerate the key pair and redeploy authorized_keys"`. **No account names in URLs, no values** |
| `readers` | no | For the incident checklist: who reads it (scripts / services / people). Used to see "what has to change when the value changes" |
| `priority` | no | Incident **handling order**: `high` / `normal` (default) / `low`. **Pure ordering — no cryptographic meaning at all** |
| `linked` | no | Entries that must be rotated together with this one (deploy key and known_hosts, a token and its CI secret). Elements must be existing entry paths |
| `aliases` | no | Old pointers, see §8 |
| `updated` | yes | Date the content last changed (written by the CLI) |

- Entry file = `store/<path>.<type>.age`. Catalog and store must match one to one: an entry without a file or a file without an entry is a `check` ERROR.
- **Naming rule**: path, title, description and tags describe only "what this is and who uses it" — **never the value, nor anything it can be inferred from**.
- **Key order (fixed; writers must follow it)**: `path`, `type`, `title`, `description`, `fields`, `target`, `acl`, `machines`, `tags`, `rotate`, `readers`, `priority`, `linked`, `aliases`, `updated`; **keys an implementation does not know are kept verbatim after `updated`**, in their original relative order. Both implementations must write byte-identical output for the same content (each needs a regression test for it) — otherwise alternating CLI and web writes produce whole-file diffs.
- **`linked` is a two-way constraint**: before deleting an entry, check who links to it; never leave a reference to a missing entry (it invalidates the referencing entry and makes the web refuse all writes).

**Materialize targets (`target`)**

- Only two prefixes are allowed: `~/` (the user's home; on Windows `USERPROFILE`, **never `HOME`** — Git Bash rewrites it) or `{workspace}/` (the directory in `SECRET_WORKSPACE`; **while it is unset, `{workspace}/` targets are refused**). The placeholder may only appear at the start. Anything else is illegal (ERROR, not materialized): `{` `}` elsewhere, `..` or `.` segments, empty segments, backslashes, a colon anywhere (drive letters included), control characters, segments ending in `.` or a space, Windows reserved-name segments (with an extension too, e.g. `nul.txt`, `COM1.log`, case-insensitive). The CLI additionally refuses reparse points (junctions / symlinks) at every level.
- **The allowed materialize roots are hard-coded in the CLI, not stored in the repo**: `~/.ssh/` and `{workspace}/`. A `target` can only choose a path inside them.
- **A first materialization, or a changed `target`, needs a human**: the CLI remembers approved `(entry path, target)` pairs on the machine (outside the repo); an unapproved pair is listed and skipped, and only `--approve` writes it. Why: threat model §15 item 1.

## 7. The three entry types (what the plaintext inside the ciphertext looks like)

| type | plaintext | use |
|---|---|---|
| `kv` | dotenv subset, below | values for scripts / services (`secret run` / `secret get`) |
| `file` | arbitrary bytes, verbatim | materialized to a path (ssh private keys, `.env`, scripts with credentials) |
| `doc` | UTF-8 markdown | for humans; rendered by the web UI |

**The `kv` dotenv subset**:

```
# comment lines (starting with #) are ignored
APP_ID=value-to-end-of-line
APP_SECRET=value-to-end-of-line
```

- Split on `\n`; strip **at most one** trailing `\r` per line. Then: blank lines and lines starting with `#` are ignored; every other line must be `KEY=VALUE`.
- `KEY` matches `^[A-Z][A-Z0-9_]*$`, no duplicates. Everything after the first `=` to the end of the line is the value — **no unquoting, no escapes, no trimming**. `KEY=` (empty value) is legal.
- Any illegal line (lowercase key, leading space, `export K=…`, no `=`) → **the whole entry fails to parse** (error, not skipped).
- Values must not contain `\r`, `\n` or NUL; writers must refuse such values (use `file` for multi-line content).
- Writers: UTF-8 without BOM, LF, every line terminated by `\n`.

**Reference syntax** (pointers in documents and CLI arguments): `secret:<path>#<FIELD>` (one kv field) or `secret:<path>` (the whole entry). Split on the **last** `#`. The `secret:` prefix is optional in CLI arguments.

**Ciphertext validity** (self-check after CLI writes; `check` and the web check on read): every `.age` file must start with the bytes `age-encryption.org/v1\n`; its repo path must match
`^store/[a-z0-9][a-z0-9-]*/[a-z0-9][a-z0-9-]*/[a-z0-9][a-z0-9-]*\.(kv|file|doc)\.age$` (plus the reserved-name exclusion). Otherwise ERROR.

## 8. Old-pointer aliases

Useful when migrating from notes / wikis / old files that used to hold the values: each item in `aliases` is `<source>:<relative path>[#<anchor>]`, where `<source>` is a name you choose that matches `^[a-z][a-z0-9-]*$` (e.g. `wiki`, `notes`, `oldrepo`, `ssh`).

- **Normalization** (on store and on compare): trim whitespace, strip outer `[[` `]]`, backslashes to forward slashes, NFC, split the anchor at the last `#`, drop a `.md` suffix from the path part. **Case-sensitive.**
- A source prefix is required and the path part must be non-empty.
- Normalized aliases (anchor included) are **globally unique**; duplicates = ERROR.
- `secret resolve <old pointer>`: exact match first (anchor included); otherwise match on the part without the anchor (possibly several, all listed). The input must carry its source prefix. Output is only `secret:<path>`; nothing is decrypted.

## 9. Identities

| Who | Private key | Notes |
|---|---|---|
| device | `~/.config/secrets/identity.txt` (on Windows `~` = `USERPROFILE`) | `age-keygen` format. Windows: inheritance broken, current user only; POSIX `0600`. Created by `secret init`; never leaves the device |
| service (e.g. the web UI) | only on that service's host, readable only by the service user | never in any repo |
| `recovery` | stored offline by the owner; optionally `recovery/recovery-identity.age` (passphrase-encrypted) | written to the desktop when generated; delete it there once stored |

- Environment overrides: `SECRET_REPO` (repo root; default `{workspace}/secrets` when `SECRET_WORKSPACE` is set, else `~/secrets`), `SECRET_IDENTITY` (identity file).
- Private keys **never go into a repo, a log or stdout**; only public keys computed with `age-keygen -y` may be printed.

## 10. `store/.recipients.lock`

```
# secret recipients lock v1
<recipient-set hash>  <ciphertext SHA-256>  store/personal/ssh/deploy-key.file.age
```

- The first line must be `# secret recipients lock v1`; then one line per ciphertext, three columns separated by **two spaces**, sorted by path ordinally ascending; no blank lines; the file ends with `\n`.
- **Covers only ciphertexts under `store/**`**; `recovery/*.age` is not in the lock (it is passphrase-encrypted, it has no recipients).
- Ciphertext hash = the raw bytes of the file in the work tree (identical to the git blob content under the `binary` attribute; the web computes it over the blob of the bare repo with the same result).
- Updated by whoever writes a ciphertext (CLI add / edit / rekey, web create / edit) **in the same commit**.
- `check`:
  - recipient-set hash ≠ what the policy yields now → **needs rekey** (ERROR);
  - ciphertext hash ≠ actual file hash → the ciphertext was changed behind the CLI's back, the lock cannot be trusted (ERROR);
  - a ciphertext in store without a lock line, or the other way round → ERROR.
- Why it exists: the age header does not record recipient public keys, so a ciphertext does not tell who it was encrypted to. The lock **is not tamper-proof** (whoever can change a ciphertext can change the lock); it catches mistakes and drift, see §15.

## 11. `.gitignore` and plaintext discipline

- **No plaintext value ever lands in the repo**: `.gitignore` ignores everything (`*`) and then **explicitly whitelists**: `/FORMAT.md`, `/README.md`, `/INCIDENT.md`, `/recipients.toml`, `/policy.toml`, `/catalog.toml`, `/store/**/*.age`, `/store/.recipients.lock`, `/recovery/*.age`, `.gitattributes`, `.gitignore`. A new root file needs a `.gitignore` change.
- Since `.age` files are let through, the header check of §7 is the second gate: the git pre-commit hook installed by the CLI (`secret hooks install` points `core.hooksPath` at `cli/githooks/` of your secret-run checkout — **not inside the data repo**, so repo content never becomes code executed on your machine) validates the header and path regex of every staged `.age` file and rejects the commit otherwise.
- The only temporary plaintext the CLI creates (the editor step of `edit` / `add`) lives outside the repo in `%LOCALAPPDATA%\secret\tmp` (POSIX `~/.cache/secret/tmp`, 0700) and is deleted right after.

## 12. `secret check` levels and exit codes (shared wording with the web `/health`)

| Level | Meaning | Exit code |
|---|---|---|
| `OK` | passed | — |
| `WARN` | needs a human but values still work (recovery key not confirmed offline, policy names a non-active recipient, a policy result without recovery, unpushed local commits, behind upstream, materialize targets waiting for approval) | 2 (if there is no ERROR) |
| `ERROR` | values will fail or there is a security problem (local identity missing / not an active recipient, lock mismatch, catalog vs store mismatch, invalid ciphertext, sample fails to decrypt, kv field names differ from the catalog, a materialized file differs from the repo, duplicate aliases, invalid TOML, a value found in a scanned log) | 1 |

Every output line is `<LEVEL> <check> <name or note>`; **only names and states, never values**.

## 13. How the web UI reads the repo

- It mounts the bare repo read-only and reads TOML and ciphertexts with `git ls-tree` / `git cat-file` at `HEAD`; ciphertext goes to `age -d -i <service identity>` over stdin, plaintext stays in memory.
- Listing and search use `catalog.toml` only, without decrypting; for `kv` only the one requested field is decrypted and returned.
- Writes go through its own work-tree clone and a deploy key (`git push`), with the same catalog / store / lock rules as the CLI.
- `/health` returns the HEAD commit and the `format` from `[[meta]]`.

## 15. Threat model (format level, accepted trade-offs)

1. **Anyone who can push to the data repo can forge entries**: age does not authenticate the sender and public keys are public. An attacker (a compromised git server, an abused web write path) can create a `file` entry encrypted to `@all` and update the lock. Mitigation: the materialize roots are hard-coded in the CLI and every new `(path, target)` pair needs human approval (§6). **Not covered**: replacing the content of an already approved `target` (e.g. swapping a private key under `~/.ssh/` or a script with credentials under `{workspace}`), replacing a `kv` value (making a script send requests with the wrong credential). A complete fix needs commit-signature verification.
2. **Anyone who can read the repo** sees all metadata (entry names, descriptions, materialize paths, recipient list), but no values.
3. **A leaked recipient private key** = every entry that recipient can decrypt is leaked, including old ciphertexts in git history; rekey is not revocation — rotate the values.
4. **A server-side reader (the web UI) holds an identity on a server**: whoever controls that server reads everything encrypted to that identity. Keep it behind an access layer (VPN, zero-trust proxy, …) and give it a narrow policy (§5).
